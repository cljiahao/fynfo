## Findings

1. **P1 — Secret variants can be accidentally committed.** `.gitignore:34-37` ignores only `.env` and `.env.local` (plus `.env.*.local` later), while constitution §8.2 specifically recognizes `.env.production`, `.env.production.*`, `.env.development`, and `.env.staging` as real secret files. `git check-ignore --no-index` on synthetic filenames confirmed those variants and `example.key` are unignored; `.env.local` is ignored. `.cursorignore:1-5` is similarly incomplete. Recommend explicit secret-pattern exclusions while preserving `.env.example`; validate with synthetic filename checks, never real contents.

2. **P1 — Harness lacks a secret-read guard for Grep/shell reads.** `.claude/settings.json:22-24` allows broad Read/Grep/Glob, `:45-52` denies selected Read paths but has no analogous Grep denies, and `:112-125` only installs Write/Edit and destructive Bash hooks. `.claude/hooks/guard-destructive-bash.mjs:5-17` has no secret-read pattern. Private-key Read paths are absent from deny entries. These are enforcement gaps relative to §8.2, not proof this Codex host permits those reads (the desktop sandbox is separate). Recommend a separately approved guard covering supported read/search tools and narrow shell data access; synthetic payload regression tests only. Exact permission matching should be tested in Claude Code before asserting absolute/nested paths are blocked.

3. **P2 — Protected edit regex assumes an absolute or slash-prefixed path.** `.claude/hooks/guard-protected-paths.mjs:9-16,36` normalizes backslashes but does not resolve relative paths: regexes begin with `/`, so `.claude/settings.json` and `.env.production` do not match, although `C:/.../.claude/settings.json` does. Settings deny entries mitigate some cases but not `.github/workflows/**` or project skills. Recommend approved path resolution against repo root and synthetic relative/absolute Windows/POSIX tests. Preserve supported owner approval flows; do not bypass a guard.

4. **P2 — Destructive Bash checks do not cover the prohibited operation family.** `.claude/hooks/guard-destructive-bash.mjs:5-17` checks `git branch -D` but not `git branch -d` (both delete branches, prohibited by §8.2), only `rm -rf` order, and only DROP TABLE SQL. The settings deny list mirrors these narrow prefixes. PowerShell deletion and destructive migrations are not generally covered. `--force-with-lease` IS caught by the existing `--force` substring; do not report that as a gap. Recommend approved narrow operation-family tests and host-appropriate policies, not a claim that regex can fully sandbox arbitrary shell code.

5. **P2 — Tests named “scoped” do not assert query scopes.** `test/helpers/fake-supabase.ts:58-60` discards all eq/in/order arguments; one mutable currentTable is shared across every builder (`:45-54,93-96`). `test/features/equity/equity-actions.test.ts:230-238`, `test/features/assets/snapshot-actions.test.ts:210-218`, `test/features/expenses/expense-actions.test.ts:165-173`, and household goal delete tests merely check table/delete count. Removing ownership/id filters would still pass. Recommend recording per-query filter arguments, using distinct builders, and asserting exact resource/user/household scopes for destructive paths. Guard mocks also always succeed; add denial-before-DB tests at representative action boundaries. Real RLS/RPC atomicity needs local database tests; fake responses cannot prove it.

6. **P2 — Coverage thresholds are optional, not a CI gate.** `package.json:23-25` maps test:ci to `vitest run` while only test:coverage enables coverage. `.github/workflows/ci.yml:38-39`, `.husky/pre-push:1`, and the Stop hook invoke test:ci. `vitest.config.ts:26-35` explicitly says coverage floors are enforced only on test:coverage, despite “gated” commentary. [Official Vitest coverage documentation](https://vitest.dev/config/coverage) confirms coverage.enabled defaults false. Recommend running existing coverage script in CI via separately approved workflow change or making test:ci enable coverage after measuring run cost. Security paths require meaningful cases as well as line percentages.

7. **P2 — Harness integrity remains off the gate and baseline drifts.** `scripts/verify-harness.mjs:5-10` normalizes LF; `.claude/skills/regen-harness/SKILL.md:28-29` hashes raw bytes. `package.json:20` excludes check:harness. Fresh `pnpm check:harness` exited 1: AGENTS.md and next-verify/SKILL.md drifted, 2/11 files. This is already documented in spec 065; do not silently bless unrelated drift. Recommend owner-approved normalized regeneration and review of each affected path, then re-enable gate. `CONSTITUTION.md` is not in the manifest, an additional baseline-scope choice for owner review.

8. **P2 — README setup instructions are obsolete and direct users to removed tooling.** `README.md:12-13,28-40,53-74,90-100,164-169` describes NextAuth/Prisma, old keys, and a dev auth bypass; current dependencies/actions use Supabase. `:110-155` references Dockerfile and scripts/build-push.sh absent from the tracked tree. Recommend rewriting actual Supabase + vault setup and existing scripts; distinguish constitutional deployment intent from artifacts actually supplied. `.env.example:5` requests SUPABASE_SERVICE_KEY although no source consumer was found; it omits ADMIN_EMAILS used at `src/features/admin/lib/get-marketing-stats.ts:28`. Remove unused elevated-secret guidance and document optional ADMIN_EMAILS. TRUST_PROXY has no current source consumer; do not reintroduce it merely because historical specs mention it.

9. **P3 — Current harness README and verification skill are stale.** `.claude/README.md:9-11,15-20,29` documents removed PowerShell hooks, flat tc4 skills, and reminder-only Stop behavior. Actual hooks are Node, injection guard and test-enforcing Stop exist. `.claude/skills/next-verify/SKILL.md:10-13` bypasses check:routes by manually chaining three checks and inaccurately describes pnpm check. `eslint.config.mjs:48-50` retains .ps1/.sh rationale after Node migration. Recommend ordinary README/comment cleanup where authorized; protected skill edits require separate approval. Dated historic plans should stay intact and be labeled historic if necessary.

10. **P3 — Route validator does not prove every legal handler form is wrapped.** `scripts/check-route-logging.mjs:26-27` strips comments using regex without distinguishing string literals; `:43-44` only matches `export const METHOD = identifier`, and function exports, but misses legal alias exports and typed const declarations. Catch-all directory read failure at `:32-36` exits success, also concealing permission/read failures. Recommend a narrow parser/testable validator using existing TypeScript tooling (no dependency), with alias/typed/string/comment tests and fail-on-unexpected-read-error. Current route idiom is recognized; this is a future enforcement gap, not a current unlogged route claim.

11. **P3 — Spec index claims nonexistent approval enforcement.** `specs/README.md:3,15-18` lacks owner-authorized audit path and says approval hash is mechanically checked, while CI only runs check/tests/build. Recommend documenting actual governance and enforcement limits. Historical specs marked shipped with blank impl_pr values or placeholder plan snippets are retained; owner may separately reconcile metadata rather than invent missing approvals.

12. **P3 — Test discovery can silently disappear.** `vitest.config.ts:19` passWithNoTests:true would produce a successful test gate if include paths were accidentally changed or tests removed. Now that 68 tracked suites exist, recommend false. Existing test-level jsdom annotations, cleanup and independent crypto oracles are useful and should remain.

## Security-critical missing cases and characterization risks

- No tracked tests exercise API track handler DB/PII boundaries, actual proxy redirect/session refresh behavior, callback origin handling, logger redaction, or withLogging exception/status behavior. Pure TrackEventSchema and isServerActionRequest tests are useful but cover narrower contracts.
- `test/api/vault.test.ts:113-117` asserts only httpOnly/path on successful cookie issuance; add strict sameSite/secure/maxAge, initialization upsert failure, malformed JSON, oversized body, canary mismatch without decryption exception, and rate-limit recording failures. Existing wrong-key/no-cookie and profile-error fail-closed cases are meaningful.
- household-keystore tests do not assert cookie security attributes or malformed-length opened key rejection. Household action tests mock RPC success; they do not prove two-member cap, replay/expiry concurrency, cross-household authorization or failed membership-write cleanup.
- action-guard tests check denial outcomes but not authentication-before-key-access order. With mocked guards, action suites do not catch accidental switching from vault context to DB-only context.
- Domain source reviewers should assess characterization tests before treating them as truth: `test/features/equity/holdings.test.ts:99-114` expects costBasis=200 after buying 10@$100 and selling 5; `test/features/equity/mwr.test.ts:82-92` expects proceeds 60 for 10@$6 sell with fee 1. These assertions mirror implementation-specific accounting, not an independent financial oracle. No financial recommendation or model change is made here.
- salary-plan's insurance exclusion shipped in spec 067 is absent from its two averaging cases. Household stale-lock-state fix in spec 068 has no hook regression suite. ExpenseQuickAdd tests cover success reset/paste but not failed-save recovery or overlapping submissions. Add tests with the relevant remediation rather than duplicating existing happy paths.
- Keystore test keeps a separate sealing implementation: useful independent envelope compatibility oracle, but comment claiming route-local encryptCookiePayload is stale since shared cookie-seal extraction. Do not automatically replace an independent oracle with the same implementation under test.
