## Findings from the initial review

### P2 — Query errors can masquerade as empty financial histories (resolved in follow-up)

Affected page entry points: Assets19/56, Equity19/48–54, Salary17/46–48, Expenses14/26–27 and DashboardOverview23–24/49/73. These use data ?? [] and loading state but omit the primary query's isError state. Providers does not enable throwOnError, and the feature useQuery hooks do not supply it. Therefore a rejected initial read can render empty charts/tables or zero totals instead of the dashboard error boundary. This is a source-supported finding; it is not an observed failure in the owner's live records. Background refetch errors can similarly leave cached values without an error indication.

Recommended bounded remediation: distinguish loading, genuine empty success and failed reads at each page, expose Retry for its failed query, and prove recovery with synthetic rejected/read-success fixtures. Dashboard components should identify unavailable datasets instead of substituting zero totals. Existing Profile, SnapshotForm and Household error handling provide reusable patterns. No schema change is needed.

[TanStack query guidance](https://tanstack.com/query/latest/docs/framework/react/reference/functions/useQuery) distinguishes pending/error/success; query failures do not automatically become route errors without the configured throwing behavior.

### P3 — Stale admin authorization comment (resolved in follow-up)

src/app/dashboard/admin/page.tsx12 describes ADMIN_USER_IDS even though the implementation gates ADMIN_EMAILS. Runtime fixtures show the intended allowlist behavior; the comment should be updated in a documentation/comment batch.

### Previously recorded limits, not new findings

Audit070's summary retains non-atomic child replacements, Supabase row-limit/pagination risks, historical tax/CPF coverage and mixed-currency cost-basis assumptions. The page workflow tests do not establish that every historical financial input is correct. ## Remediation update — 2026-10-09

Dashboard asset and salary rows distinguish pending, successful-empty and failed reads independently. Loading no longer displays false zero totals; failed reads expose opaque retry states. Assets, Equity, Salary and Expenses also handle primary read failures explicitly. Snapshot-dependent calculations wait for known snapshots, and mounted planning/allocation content is hidden during temporary snapshot unavailability to retain unsaved local edits. A regression exercises snapshot and expense background failure/retry with freshly queried allocation inputs.

Summary rendering calculates totals for only the latest two snapshots, preserving latest and previous-month comparisons. A100-month synthetic history reproduced the unnecessary older-month calculations before this fix. This is a rendering-work reduction; actual database/network latency was not measured. Initial unlocked server prefetch is already parallel. Post-unlock client Server Function calls can queue, as described in [Next.js documentation](https://nextjs.org/docs/app/getting-started/mutating-data). Any aggregate-read redesign needs its own recorded security/behavior verification.
